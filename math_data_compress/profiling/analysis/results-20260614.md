## The findings that matter (ranked by upside)

### Tier 1 — clear, large headroom

**thomas-cuda — occupancy-starved.** Theoretical occupancy 56%, **achieved 9.95%**
(6.4 active warps/SM out of 64). Grid is only 257 blocks × 64 threads ≈ 16K threads
spread over 80 SMs — the GPU is barely filled, and each thread runs a *serial* forward+
backward sweep (long dependency chain) with nothing to hide its latency. Memory is 55%
but that's misleading — the real problem is not enough warps in flight.
→ **Lever:** map more parallelism — many more systems in flight, or a parallel
tridiagonal algorithm (CR/PCR) so each system uses multiple threads. Big upside.

**gaussian-cuda — launch-overhead pattern.** `fan2` (the real work) is a healthy 76%
memory-bound kernel. But `fan1` is launched **once per elimination step (~4095 times)**,
each a 3.7 us kernel on a grid of **16 blocks** at **11% occupancy** doing almost nothing
(0.3% compute, 8% memory). This is exactly the Floyd-Warshall shape you already beat 5.43×.
Total kernel time 499 ms, device offload 950 ms → host-submission overhead is huge.
→ **Lever:** kill the per-step `fan1` launches (fuse pivot-normalization into `fan2`,
or block the elimination). High upside, low risk.

**jaccard-cuda — one kernel owns everything.** `jaccard_is_opt` is **7.75 ms** vs the
other kernels at 11–36 us — it is ~99% of GPU time. It runs at 49% compute / 34% memory
but only **20% occupancy** with a 3D block (8,4,8) and grid (1,1,128). Nested CSR loops +
`atomicAdd` on `weight_i`, heavy divergence from variable row lengths.
→ **Lever:** raise occupancy (better block shape), balance work per-nnz instead of
per-row, cut atomics. Upside is large but data-dependent / higher risk.

### Tier 2 — real but bounded

**bscan-cuda — single-warp blocks.** `binary_scan` launches **block size 32** (one warp),
capping theoretical occupancy at 50%, achieving 46%. Compute 7% / memory 8% — it's
neither; it's just not enough work resident. The run.log even shows throughput scaling
cleanly with block size (32→1024 = 11→91 Belem/s), confirming small blocks under-utilize.
→ **Lever:** larger blocks with `__ballot_sync`+`__popc` for the binary prefix (one
instr/warp), multiple warps per block. Clean rewrite, likely solid win.

**scan-cuda — sync-heavy, half occupancy.** `scan<char,128>` is genuinely
memory+compute-bound (87%/78%) which is good, but occupancy is only **49%** and the
Blelloch sweep is barrier-heavy (log N `__syncthreads`). The bcao (bank-conflict-avoiding)
variant only helps for 4–8 byte elements (run.log: +28% at size 4, *negative* at size 1).
→ **Lever:** warp-scan via `__shfl` to cut barriers, vectorized global I/O, raise
occupancy. Moderate, well-trodden.

### Tier 3 — already near ceiling (defend, don't chase)

**atomicReduction-cuda** — 77% memory, 92% occupancy, ~850 GB/s of V100's ~900 peak.
Little honest headroom. Block-level reduction before the global atomic might shave a few %.

**filter-cuda** — 66% memory, 90% occupancy. Streaming compaction near bandwidth.
Vectorized loads / fuller warp-aggregation = small gains.

**jacobi-cuda** — 73% memory, 85% occupancy, well-tuned stencil. The only lever is the
per-iteration `atomicAdd(error)` reduction + host convergence loop launch count; modest.

**histogram-cuda** — already has the smem-privatization win baked in (smem ≫ gmem in
run.log). The profiled launch shows low 20% occupancy on `smem_atomics`, so there may be
a small occupancy lever, but the pattern is sound.

---

## Recommended optimization order

1. **thomas** — occupancy 9.9%; most underutilized kernel, clear parallelism lever.
2. **gaussian** — proven launch-overhead pattern (your 5.43× FW shape), low risk.
3. **jaccard** — one 7.75 ms kernel = ~99% of runtime; big but data-dependent.
4. **bscan** — single-warp blocks; clean ballot/popc rewrite.
5. **scan** — barrier-heavy at 49% occupancy; warp-scan + vectorized I/O.
6. **histogram / filter / atomicReduction / jacobi** — near ceiling; confirm we match
   or marginally beat baseline rather than chase headline speedups.

This reorders the pre-profiling guess: **thomas jumped to #1** (the 9.9% occupancy was
invisible from source alone), and the four bandwidth/well-tuned kernels are confirmed
low-headroom.
